【背景知识】
      Electron是基于Chromium+Node.js的桌面应用框架。采用主进程+渲染进程多进程模型，主进程运行Node.js负责应用生命周期，渲染进程运行Chromium内核呈现HTML5界面。通过集成V8引擎，使Web前端技术栈与底层系统功能结合，开发者可用JavaScript构建跨平台桌面应用。
  
    其他平台Electron开发流程：
  
   
  【解决方案】
 1. Electron版本选择：  当前已提供两个HarmonyOS化版本：Electron25和Electron34，可以使用华为账号登录仓库下载最新版本的Release包，这两个版本对应的Chromium内核和node.js版本情况如下：
               Electron25    Electron34    Electron37   
       Chromium    Chromium114        Chromium132
        Chromium138   
       Node.js    18.18.2    20.18.1    22.16.0   
     在选择Electron版本时，需要考虑以下几点：
    Electron版本及Node.js版本是否满足应用使用三方库需求。
  对于前端库，需检查其依赖的浏览器API是否被选择的Electron版本对应Chromium版本支持。
   如果是由其他平台迁移至HarmonyOS，以尽快完成HarmonyOS化为目的的话，可以考虑使用与其他平台版本更接近的Electron版本，否则出于版本迭代考虑，更推荐使用更新版本Electron。
 2. 整体迁移思路如下：  
    分析依赖，对不满足的依赖进行适配和替换。
  业务代码适配HarmonyOS，对差异点如权限判断，平台判断，沙箱路径等进行修改。
  TypeScript开发可选：编译TypeScript为JavaScript。
  将编译产物及package.json复制到HarmonyOS化Electron样例工程中，并删除package.json的devDependencies字段。
  在HarmonyOS的Electron工程中安装依赖，并启动工程，查看依赖是否正常。若不正常，则回退到第1步进行依赖适配。
    最佳实践：
 
  
   1.原始Electron工程和HarmonyOS Electron工程互不包含，分别使用VSCode/WebStorm和DevEco Studio打开两个工程。 2.Electron工程编译并使用electron-builder打包，其中package.json中build字段设置asar: false，拷贝asar拆包后的app文件产物到HarmonyOS Electron工程目录。
 
  
   3.替换node_modules中C/C++ Native模块为使用HarmonyOS编译工具链编译的产物，并将相关.node/.so放置在ohos_hap\electron\libs\arm64-v8a目录下，并修改引入路径。
 
 3. 编译常见问题：调用与接口声明不一致。 问题描述：      问题1：TS开发的Electron项目，调用SystemPreferences请求权限接口报错。
     报错：error TS2339: Property 'requestSystemPermission' does not exist on type 'SystemPreferences'.`。
  
  
    问题2：TS开发的Electron项目，使用const currentPlatform: NodeJS.Platform = 'win32'判断currentPlatform === 'ohos'平台时发生报错。
     报错error TS2367: This comparison appears to be unintentional because the types 'win32' and 'ohos' have no overlap.
  
  
  问题1&2根因分析：  
  HarmonyOS的Electron相比开源版本，在Electron层新增了暴露的接口，如权限相关接口。Windows环境的接口声明（electron.d.ts）没有HarmonyOS的权限接口，因此TS编译阶段报错。
 修改方案：    问题1： 使用HarmonyOS化的Electron源码中src/electron/electron.d.ts替换掉业务代码里的node_modules/electron/electron.d.ts。
   
    问题2： Node.js原始接口声明中没有ohos，HarmonyOS版本的Node.js为了和开源版本保持一致，暂不在Platform中新增ohos。
   
  因此建议开发者使用process.platform进行判断。
 其他同类错误也可使用问题1和2的解法一并解决：            序号    错误码    中文描述   
           1    TS2345    参数赋值时类型不匹配所以赋值失败。   
       2    TS2554    实参和形参个数不匹配   
       3    TS2346    参数类型X不能赋值给参数类型Y，通常出现于函数重载场景   
       4    TS2339    调用了不存在的属性   
       5    TS2684    泛型约束不匹配   
       6    TS2769    没有对应的重载方法。   
       7    TS2564    属性没有初始化器，也未在构造函数中明确赋值。   
       8    TS2367    变量比较时类型不匹配   
    
  【总结】 Electron项目适配HarmonyOS PC，主要工作是使用HarmonyOS适配版Electron重新打包构建应用，并替换掉不兼容Node插件模块集成的功能。 如果使用TS开发Electron项目，迁移过程中TS转JS失败是常见易错点之一。若出现以上错误码，从接口声明方向排查。
  【常见FAQ】 Q：HarmonyOS开发需要使用.node，在Electron工程中引入后，yarn build报错error TS2307: Cannot find module xxx。 A：yarn build:tsc本身并不自动检查.node文件，请检查是否手动配置了相关校验。
  Q：Electron工程中引入.node，指明了const addon = require('/data/storage/el1/bundle/libs/arm64/libaddon.node')，使用webpack编译后移植到HarmonyOS工程中运行，HarmonyOS工程对应位置已引入了该node，但运行时仍报错Cannot find module '/data/storage/el1/bundle/libs/arm64/libaddon.node'。 A：配置webpack的externals，让webpack不对这个addon模块进行解析和打包，保留require语句的原样，在运行时再去加载。在webpack.config.js的externals字段中添加'libaddon.node': 'commonjs /data/storage/el1/bundle/libs/arm64/libaddon.node'后可以直接const addon = require('libaddon.node')。
  Q：在Electron开发中，如何判断当前的平台是HarmonyOS？ A：可以通过node.js的process.platform进行判断，HarmonyOS平台输出的字段是openharmony。

使用electron开发HarmonyOS PC应用，如何执行cmd命令？请以wmic为例说明。

--- post 0301194087407933252 author=393eaf0f10544b699d3a54316f6f2bc7 date=None first=0 ---
【背景知识】 exec：Node.js的子进程模块中的一个方法，用于执行shell命令并获取其输出，具体使用参考exec的使用。
 【解决方案】
1. 使用命令行获取os名称和版本。 a、windows上使用wmic获取os名称版本和os所在磁盘编号：
   C:\Users\用户名>wmic os get Name。 Name。 Microsoft Windows 11 专业版|C:\windows|\Device\Harddisk0\Partition3。
 
 b、ubuntu 22.04上获取os名称和系统所在硬盘编号：
   ******@wuhphis40368:~$ lsb_release -d Description: Ubuntu 22.04 LTS $ df -l / Filesystem 1K-blocks Used Available Use% Mounted on /dev/vda2 61663000 19477544 39243808 34% /
 
 c、HarmonyOS上获取os名称和版本：
   $uname -a HarmonyOS localhost HongMeng Kernel 1.9.5 #1 SMP Fri May 23 11:02:06 UTC 2025 aarch64 $df / Filesystem 1K-blocks Used Available Use% Mounted on tmfs 16313040 68 16312972 1% /data/storage/el2
 
2. 通过exec方法在HarmonyOS PC上调用命令行，样例如下。 a、 index.html运行在渲染进程中，点击"获取系统和版本"按钮触发。
 <body>
<h2>获取系统和版本演示</h2>
<button id="getName">获取系统和版本</button>
<script>
    const { ipcRenderer } = require('electron');
    const getName = document.getElementById('getName');

    getName.addEventListener('click', () => {
      // 发送获取系统和版本请求到主进程
      ipcRenderer.send('get-name');
    });
    // 监听返回结果
    ipcRenderer.on('getName-result', (event, message) => {
      window.alert('message = ' + message);
    });
</script>
</body>

 b、主进程通过ipcMain监听事件，执行uname -a并给渲染进程返回结果。
 function getName(event) {
    try {
        const cmd = `uname -a`
        exec(cmd, (err, result) => {
            if (err) {
                console.error('获取失败:', err);
                event.reply('getName-result', `error: 命令错误`);
                return;
            }
            event.reply('getName-result', result);
        })
    } catch (e) {
        event.reply('getName-result', `error: ${e.message}`);
    }
}

ipcMain.on('get-name', (event) => {
    getName(event)
})

 效果如下：
 
 c、exec执行命令的返回值。 exec的回调函数有3个入参：error、stdout、stderr。
   error：错误对象。这是最重要的返回值。
    如果命令成功执行（即使命令本身有错误输出），error为null。

        Q：执行./electron_build.sh进行编译的时候为什么会出现如（cannot access 'rust-toolchain.tar.gz' : No such file or directory）类似的报错？

      （1）实现接口---systemPreferences.getMediaAccessStatus(mediaType)

  五、坚盾守护模式
        坚盾守护模式是为高安全需求用户设计的系统级安全防护方案。该模式通过实施严格的功能限制，显著增强系统安全性，有效防范针对远程攻击面的各类威胁。在坚盾安全模式下，系统增加了功能限制，需要开发者评估应用在坚盾模式下的可用性。
  5.1 启用坚盾守护模式
        要启用坚盾守护模式，请按以下路径操作：
        （1）进入电脑系统设置
        （2）选择"隐私和安全"选项
        （3）点击"坚盾守护模式"并开启
  5.2 坚盾守护模式下的功能限制
        为降低应用受攻击风险，坚盾守护模式将实施以下关键安全限制：
  • 全面禁用即时编译(JIT)功能，包括已获取 ACL 权限的应用程序
  • 暂停 WebAssembly 支持（当前版本中 WebAssembly 依赖 JIT 功能实现）

       （2）WebAssembly 兼容性检查：
  • 静态代码分析：检查项目中的 WebAssembly 相关API调用，与第三方库的 Wasm 依赖情况。
  • 运行时验证：在坚盾守护模式下执行全功能测试。

要先区分目标是 HarmonyOS PC 还是手机/平板 HAP。PC 侧如果走 Electron 适配路线，整体思路接近把现有 Electron 工程搬到鸿蒙 Electron 壳里，再处理 native module、路径、窗口和系统能力差异。
    如果目标是普通 HarmonyOS 应用内用 ArkWeb 承载界面，就不建议默认假设可以像桌面一样长期运行一个本地 Node Web 服务。HAP 里后台进程、端口监听、文件系统、native 模块、PTY/SSH 等都有生命周期和沙箱限制。
    对 electerm 这类项目，更可控的迁移路线是：前端 UI 尽量复用为 H5/ArkWeb 或 ArkUI；核心能力如 ssh、sftp、pty、终端渲染、密钥管理拆成 ArkTS/NAPI/Native 能力；WebView 只负责界面展示。这样比“启动 Node 服务再打开本地页面”更符合移动端和鸿蒙应用模型。

--- post 0301208607403321082 author=393eaf0f10544b699d3a54316f6f2bc7 date=None first=1 ---

【背景知识】
  当前仅支持Linux_x86环境交叉编译，推荐使用Ubuntu22.04。
  【解决方案】
      通过git clone <仓库URL> --branch <分支名>拉取HarmonyOS化Electron源码，分支与Electron版本对应关系如下（前缀和后缀可能更改，请在仓库中复制具体分支名，勿在此复制）：
                        Electron25     Electron34     Electron37    
               对应分支     xxx/114.0.5735.248-xxx     xxx/132.0.6834.161-xxx     xxx/138.0.7204.45-xxx    
       
  
   克隆过程中需输入Username和Password（如果反复提示输入Username和Password，则是Username或Password错误），通过右上角SSH密钥/HTTPS密码查看并设置(如果Username为空值，需要实名认证)。
   
   
   注意源码中包含LFS大文件，拉取后执行git lfs pull检查大文件是否完整拉取，若无反应，则拉取完成。
   因仓库较大，拉取耗时较长，输入Username和Password后拉取可能耗时5~10分钟，非卡死。
  并且建议拉取时指定分支，否则checkout分支多次耗时。
  
    拉取源码完成得到chromium-electron-release，进入chromium-electron-release/src/ohos_sdk目录，执行.install文件。执行完成后会新增toolchains、openharmony、native等文件夹。
   
   仅编译node需要工具链的情况下，按以上操作获取即可，无需编译Electron源码。libelectron.so可以从electron-release构建包中获取，相应地注意修改编译配置CMakeLists.txt或binding.gyp中链接的libelectron.so的路径。
  
    配置环境变量为HarmonyOS编译工具链。可以写成set_env.sh文件在每次编译前执行，也可以写在环境变量中。
   export CC="${Electron源码路径}/src/ohos_sdk/openharmony/native/llvm/bin/clang --target=aarch64-linux-ohos"
export CXX="${Electron源码路径}/src/ohos_sdk/openharmony/native/llvm/bin/clang++ --target=aarch64-linux-ohos"
export LD="${Electron源码路径}/src/ohos_sdk/openharmony/native/llvm/bin/lld --target=aarch64-linux-ohos"
export STRIP="${Electron源码路径}/src/ohos_sdk/openharmony/native/llvm/bin/llvm-strip"
export RANLIB="${Electron源码路径}/src/ohos_sdk/openharmony/native/llvm/bin/llvm-ranlib"
export OBJDUMP="${Electron源码路径}/src/ohos_sdk/openharmony/native/llvm/bin/llvm-objdump"
export OBJCOPY="${Electron源码路径}/src/ohos_sdk/openharmony/native/llvm/bin/llvm-objcopy"
export NM="${Electron源码路径}/src/ohos_sdk/openharmony/native/llvm/bin/llvm-nm"
export AR="${Electron源码路径}/src/ohos_sdk/openharmony/native/llvm/bin/llvm-ar"
export CFLAGS="-fPIC -D__MUSL__=1"
export CXXFLAGS="-fPIC -D__MUSL__=1"
